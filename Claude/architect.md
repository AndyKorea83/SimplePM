# Архитектура

Этот документ фиксирует **решения** и их обоснование — не пересказ кода (структура папок и что где лежит — в @CODE.md). Обновляется по мере появления новых архитектурных решений.

## Backend

### Слои

Чистая архитектура, разделение по каталогам `internal/`:

- `entity` — доменные модели, без JSON-тегов и presentation-специфичных полей (например, `time.Duration`, а не часы).
- `repository` — интерфейсы доступа к данным + их реализации (`mspdi` — чтение XML, `memstore` — in-memory хранилище с мутациями).
- `usecase` — бизнес-логика, оперирует `entity.*` и интерфейсами `repository`, не знает про HTTP.
- `delivery/http` — маршрутизация (`chi`), HTTP-хендлеры, DTO (`dto.go`) — здесь и только здесь появляются JSON-теги и форматирование дат/чисел под фронтенд.

Интерфейсы, которые нужны конкретному usecase от репозитория, объявляются **в месте использования** (`internal/usecase/project.go`: `projectRepository`, `internal/usecase/timesheet.go`: `timesheetDataset`), а не в пакете `repository` — так реализациям (например read-only `mspdi.FileRepository`) не приходится притворяться, что они поддерживают запись.

### Хранение данных Ганта (Этап 1 / PoC) — мульти-проектный memstore (issue #64)

- `mspdi.FileRepository` читает XML **один раз** при старте процесса (`cmd/server/main.go`) — только для затравки самого первого проекта (ID=1).
- Результат оборачивается в `memstore.Repository` — единственный источник правды на весь жизненный цикл процесса, теперь хранящий **несколько** проектов (`map[int]*projectEntry`, каждый со своими счётчиками `nextTaskUID`/`nextAssignmentUID` — задачи разных проектов не обязаны иметь глобально уникальные UID, только в пределах своего проекта). Создание/изменение/удаление задач мутирует in-memory копию нужного проекта; каждый метод `ProjectRepository`/`TaskRepository` принимает ведущий `projectID`.
- Новые проекты появляются двумя путями: `CreateProject` (пустой проект — `StartDate`/`FinishDate` выставляются в today, **не** zero-time, иначе фронтовая сетка Ганта получает `Invalid Date` из пустой строки) и `ImportProject` (парсинг уже сделан на уровне `usecase` через `mspdi.Parse` — сам `memstore` не должен знать формат файла; берёт готовый `*entity.Project` и переопределяет Name/Title/Description/CreatedBy/CreatedAt/ID данными формы).
- `ListProjects` **обязан** сортировать по ID перед возвратом — порядок обхода Go-map рандомизирован, без явной сортировки список на странице «Проекты» перемешивался бы на каждый запрос. Найдено вручную в браузере (не гипотетический баг), покрыто тестом `TestListProjects_OrderedByID`.
- Перезапуск сервера сбрасывает состояние к содержимому XML для проекта 1 (остальные, созданные/импортированные за время работы, теряются) — осознанное решение уровня PoC, а не забытый баг. Реальная персистентность (Gitea + MySQL) — Этап 2 роадмапа.
- Пример решения, вынесенного на согласование с пользователем (а не принятого по умолчанию): при реализации issue #11 (формы создания/редактирования задачи) стоял выбор — писать обратно в XML, держать мок только на фронтенде, или in-memory на бэкенде. Выбран **in-memory на бэкенде** — баланс между "по-настоящему работает через API" и не усложнять PoC реальной персистентностью. Issue #64 (страница «Проекты») продолжает тот же выбор, просто масштабируя его на N проектов вместо одного — пользователь подтвердил полное внедрение сразу, а не отложенную заглушку.
- **«Кем создан» (`CreatedBy`)** — в приложении нет аутентификации вообще. Поле — константа-заглушка (`memstore.placeholderCreatedBy`, "Текущий пользователь"), проставляется при создании/импорте, а **не** поле формы: пользователь явно решил, что со временем здесь будет отображаться реальный залогиненный пользователь, а не текст, который вводится вручную каждый раз.

### Открытие/закрытие проекта (issue #67)

- `entity.Project.ClosedAt *time.Time` — `nil` означает "открыт". Правится через тот же `PATCH /api/projects/{id}` (`UpdateProjectInput.Closed *bool`), что и метаданные — отдельного роута под закрытие/открытие нет.
- Повторное закрытие уже закрытого проекта **не** сдвигает `ClosedAt` (проверка `e.project.ClosedAt == nil` перед установкой) — иначе случайный повторный клик тихо перезаписывал бы момент закрытия.
- `usecase.ProjectSummary.Closed` — вычисляемое поле (`p.ClosedAt != nil`), а не сырой `*time.Time` наружу — DTO-слой не должен разбирать nil-указатели entity сам.
- **Полноценная история открытий/закрытий (лог событий с датами) сознательно не строится сейчас** — явное решение пользователя ("в дальнейшем необходимо будет сохранять историю открытия"), хранится только текущее состояние. Если/когда это понадобится, потребуется отдельная сущность-журнал, а не расширение `ClosedAt` до слайса.
- Фронтенд: фильтр «Открытые/Закрытые» на `ProjectsPage` — **фильтрация на клиенте** (весь список уже приходит через `GET /api/projects`), не отдельный query-параметр — оправдано PoC-масштабом (несколько проектов), пересмотреть при реальном объёме данных.

### Экспорт проекта в MSPDI XML (`mspdi.Write`, issue #64)

- Писателя не было вообще — только `Parse`. `Write` покрывает исключительно те поля, что реально моделирует `entity.Project` (Name/Title/StartDate/FinishDate/Tasks/Resources/Assignments), а не полную схему MS Project (`Calendars`/`SaveVersion` и т.п. не хранятся — писать туда нечего). Итог "похож" на `samples/project.xml`, но не побайтовый клон её схемы — сознательный выбор, не полнота ради полноты.
- **Ключевая ловушка — порядок задач.** `Parse`/`assignParentUIDs` восстанавливают иерархию из **порядка документа** + `OutlineLevel` (родитель — ближайшая предыдущая задача с меньшим уровнем), а не из явных ссылок. Но `memstore.CreateTask` всегда делает `append` в конец среза `Tasks`, независимо от того, где сидит родитель — то есть хранимый порядок **не** совпадает с порядком дерева после любой мутации. `orderedByHierarchy` в `writer.go` пересобирает depth-first обход из `ParentUID` перед сериализацией — без этого шага экспорт-затем-импорт молча исказил бы структуру дерева. Проверено round-trip тестом (`Parse` → `Write` → `Parse`, сверка иерархии/зависимостей/дат).
- `intBool` (Milestone/Summary) получил `MarshalText` — раньше был только `UnmarshalText`, обратного пути для записи не было.
- `xmlns` в корневом `<Project>` **не** появляется от одного только `xml.Name{Space: ...}` — `encoding/xml` требует явного поля с тегом `xmlns,attr` (`XMLNS string \`xml:"xmlns,attr,omitempty"\`` в `xmlProject`), иначе Marshal тихо не пишет атрибут вообще. Проверено вручную (`go run` isolate-тест), не предположение из документации.

### Даты и время: всегда сравнивать по календарному дню, а не по timestamp

Даты приходят из разных источников с разным временем суток (типичный экспорт MSPDI — 08:00 старт/17:00 финиш; правки через фронтенд — 00:00, т.к. date-only ввод). Отсюда правило: **любое сравнение "раньше/позже" между датами задачи должно игнорировать время суток**, иначе:
- `validateRange` в `memstore` некорректно отклонял бы однодневный диапазон, если у `finish` время суток раньше, чем у `start` (тот же календарный день) — сравнивает `truncateToDate(finish)` vs `truncateToDate(start)`.
- `deriveStatus` (фронтенд, `Gantt/status.ts`) без этого помечал бы задачу как "Просрочено" в день её же дедлайна, как только текущее время суток обгоняет время в `finish` — сравнивает `startOfDay(finish)` vs `startOfDay(today)`.

### Пересчёт трудозатрат (Duration) — только рабочие дни, только при явном изменении дат

`Task.Duration` — это эффорт-часы (изначально из MSPDI, либо выставляются при создании/правке), не календарная протяжённость. Правило (`memstore.businessDaysDuration`):
- при `UpdateTask` пересчитывается **только если** `input.Start != nil || input.Finish != nil` — правка одного `PercentComplete` не должна попутно менять оценку;
- пересчёт — количество рабочих дней (Пн–Пт) между датами × 8ч, без выходных, а не `finish.Sub(start)` (что посчитало бы выходные и не совпадало бы с видимой на диаграмме длительностью).

### Зависимости между задачами (issue #39)

- Тип связи хранится как MSPDI-совместимый int (`entity.DependencyType`), нумерация **не алфавитная**: ОО=0 (FinishToFinish), ОН=1 (FinishToStart, самый частый), НО=2 (StartToFinish), НН=3 (StartToStart) — так задано форматом MSPDI; "исправлять" на алфавитный порядок нельзя, будет расхождение с исходными XML-данными. Конвертация DTO→entity — `toDependencies` в `dto.go`, с тем же предупреждением в комментарии.
- Запись идёт через существующие `POST/PATCH /tasks` (как `assigneeResourceUids` — полная замена списка целиком), отдельного эндпоинта под зависимости нет.
- Валидация в `memstore.validateDependencies` (под `r.mu.Lock()`, рядом с `validateRange`): самоссылка, несуществующий предшественник, дубли в одном входном срезе, `Type` вне диапазона 0..3 — отклоняются как ошибка запроса, а не тихо игнорируются.
- Циклы обнаруживаются отдельно (`hasDependencyCycle` — BFS/DFS по графу зависимостей всех задач с подстановкой предлагаемых зависимостей для редактируемой задачи). Это авторитетная проверка; фронтенд дополнительно исключает заведомо цикличные варианты из UI выбора предшественника, но финальное решение всегда за бэкендом.
- `DeleteTask` подчищает "осиротевшие" зависимости у выживших задач (`filterDependencies`) — без этого удаление предшественника оставляло бы у преемника ссылку на несуществующий UID.
- `PercentComplete` группы (summary-задачи) считается автоматически (`recomputeSummaryProgress`) — взвешенный роллап по `Duration.Hours()` дочерних задач (вес 1 для нулевой длительности/вехи), пересчитывается при `NewRepository`/`CreateTask`/`UpdateTask`/`DeleteTask`. `UpdateTask` **отклоняет** прямую правку `PercentComplete` для summary-задачи — процент группы нельзя выставить вручную, только через прогресс подзадач.

### Гант и Календарь — независимые предметные области

По явному решению пользователя, страница "Календарь" (учёт времени по дням) **не переиспользует** `entity.Project/Task/Resource`. У неё собственные сущности (`entity.Timesheet{Employee,Theme,Task,Entry}`, пакет `internal/timesheet`) и собственный синтетический генератор данных (детерминированный seed, генерируется один раз при старте — реальных данных учёта времени пока не существует ни в каком источнике). Если оба домена впоследствии потребуется связать (например, трудозатраты по реальным задачам Ганта) — это отдельное архитектурное решение, требующее отдельного согласования, а не то, что можно вывести из текущего кода.

### Раздел QA — независимый домен, изменяемый in-memory датасет (issue #69)

Kanban-доска/отчёт по багам/история статусов/метрики построены по тому же принципу изоляции, что Календарь: `entity.Bug`/`entity.BugHistoryEntry` (пакет `internal/entity/qa.go`) не переиспользуют `entity.Task` — исполнитель/репортер это строки (имена), не ссылки на `entity.Resource`. Генератор — `internal/qa.Generate()`, тот же детерминированный fixed-seed подход, что `internal/timesheet.Generate()`.

- **Статус vs флаги — тот же принцип, что `entity.Task.IsBlocked`.** `Bug.Status` — одна из 5 колонок Kanban (To Do/In Progress/Ready for QA/QA in progress/Done). `IsBlocked`/`IsPaused` — независимые флаги поверх статуса: на доске они переопределяют обычную колонку по статусу и уводят карточку в "Blocked & paused" вне зависимости от Status. `IsQuestion` — ещё один независимый флаг, влияет только на панель "Требует внимания" страницы метрик, не на доску.
- **Severity (Критичность) и Priority (Важность) — две независимые оси**, не одна шкала: баг может быть тривиальным по критичности, но приоритетным для конкретного релиза (или наоборот). Не путать при дальнейшем расширении.
- **Исполнитель и репортер — два разных пула людей**, не альтернативные подписи одного и того же человека: исполнитель (`AssigneeName`) — разработчик, чинит баг; репортер (`ReporterName`) — QA-инженер, нашёл баг. Отчёт по багам группирует по исполнителю, лидерборд страницы метрик — по репортеру. В Figma-макете это видно по тому, что имена в Kanban/отчёте (Стребков/Петров/Смирнов) и в лидерборде метрик (Иванов/Петрова/Сидоров/...) — разные множества, это не совпадение, а отражение разных ролей.
- **Датасет мутируемый, не read-only** (в отличие от timesheet, у которого нет create/update): перетаскивание карточки на Kanban-доске меняет статус бага. `qa.Dataset` получил свой `sync.RWMutex` + `UpdateBugStatus` прямо в пакете `internal/qa` (тот же приём, что `memstore.Repository` для проекта), а не через отдельный repository-слой — для одного мутируемого поля (Status) полноценный repository-интерфейс был бы лишней прослойкой.
- **"Переносы" (транзишены) — счётчик обратных переходов статуса в истории** (баг не прошёл QA, отправлен на доработку), вычисляется по ординалу статуса (`statusOrdinal` в `usecase/qa.go`) — не хранится отдельным полем. Генератор изредка вставляет один такой "отскок назад" в путь статуса, чтобы метрика была не всегда нулевой.
- **Время жизни (лайфтайм) считается только по закрытым (Done) багам** в статистике по темам — у ещё открытого бага оно не финально, включение исказило бы среднее.
- **Роуты плоские `/api/qa/...`**, сиблинги `/api/projects`/`/api/timesheet`, не вложены под projects — независимая предметная область (тот же принцип, что уже задокументирован для timesheet).
- **Фронтенд: `Pill` (цветная плашка критичности/важности/темы/метки) — в `components/QA/`, не `components/ui/`**: переиспользуется внутри раздела (Kanban/отчёт/метрики), но не нужен другим разделам — выносить в общие компоненты только то, что нужно ≥2 фичам (тот же принцип, что и остальная библиотека `ui/`).
- **Статус как цветная плашка — только в модалке истории.** В Kanban-карточке и таблице отчёта статус — обычный текст, не плашка: так в самом макете (разные представления одного поля для разных контекстов, не недосмотр).
- **Drag-and-drop — нативный HTML5 Drag and Drop API**, без сторонней библиотеки: в проекте не было ни одной drag-and-drop зависимости, а для одноуровневого переноса карточки между колонками нативного API достаточно (см. `components/QA/KanbanCard.tsx`/`KanbanColumn.tsx`). "Blocked & paused" исключена из drag-and-drop как источник и как цель — колонка не соответствует значению статуса (см. выше), перетаскивание туда/оттуда не имеет однозначного статуса для записи.
  - **`allowDragAndDrop` — обязательный проп `KanbanPage`, не внутреннее решение компонента** (правка по ревью пользователя): эта же доска понадобится ещё в одном разделе с другими колонками, и там drag-and-drop нужен или не нужен независимо от QA — на доске QA (`App.tsx::pageForQaChild`) он явно передаётся `false`.
- **Тема (проект/подсистема) — открытый список без фиксированной палитры в макете**: цвет плашки назначается детерминированно по хэшу названия (`themeColor` в `qaColors.ts`), а не по явному маппингу с бэкенда.
- **Severity (Критичность) — цвета взяты как официальные именованные токены дизайн-системы** (`severity/blocker: #E11D21` и т.д.), найдены на карточке "Распределение по критичности" страницы метрик (node `309:8140`) — правка по ревью пользователя, отменяет более раннюю версию `SEVERITY_COLORS`, где цвета были приближены по аналогии (сам критичности-скейл на Kanban-карточке/таблице отчёта таких цветов не показывал напрямую).
- **Абсолютные числа страницы метрик не совпадают с примером в Figma** (там ~293 бага за год, сгенерированный датасет даёт 62) — два независимых макета с разными иллюстративными данными, честный расчёт по реальному датасету важнее совпадения с константами одного скриншота (тот же прецедент, что несовпадение названий тем/проектов между разными страницами макета).
- **Отчёт по багам не растягивается на всю ширину, прижата к сайдбару** (правка по ревью, дважды — первая версия выравнивала таблицу по правому краю, это было неверно): таблица зафиксированной ширины (сумма колонок 520+120+110+110+120+120, колонка "Задача" расширена до 520px, чтобы длинные названия не переносились), прижата к левому краю контентной области — как остальные страницы приложения, а не к правому.
- **Диаграмма "Распределение критичности по месяцам" — число месяца растёт вместе со столбцом, сегменты визуально разделены** (правка по ревью): раньше высота столбца считалась внутри `flex-1`-обёртки, которая почти всегда занимала всю доступную высоту (заполняя оставшееся пространство flex-контейнера) — из-за этого число над столбцом оказывалось у самого верха графика, а не над реально видимым (часто коротким) столбцом. Группа "число + столбец" в `QaMetricsPage.tsx::DistributionChart` теперь сама получает высоту, пропорциональную `total/maxTotal` (константа `BAR_MAX_HEIGHT`), число и столбец двигаются вместе. Между сегментами разных типов багов внутри столбца — тонкий `border-top` цвета фона страницы (не задевает пропорции высоты, т.к. `box-sizing: border-box`). Тот же приём (тонкий `border`, теперь `border-left`) применён и к горизонтальной шкале лидерборда — сегменты severity внутри неё раньше тоже сливались в сплошную заливку без разделения. В обоих местах разделители расставляются по индексу уже отфильтрованных (`count > 0`) сегментов, а не по индексу в `SEVERITY_ORDER` — иначе первый реально видимый сегмент мог бы ошибочно получить левую/верхнюю границу, если предшествующие ему по шкале severity имели нулевой count.
- **Метрики: тот же контрол выбора месяца, что и Календарь, без растяжения на всю ширину** (правка по ревью): `Calendar/MonthPicker.tsx` вынесен в `ui/MonthPicker.tsx` (параметризован `rangeStart`/`rangeEnd`, тот же приём промоушена компонента по факту второго потребителя, что `ThemeToggle`) — `Calendar/MonthPicker.tsx` остался тонкой обёрткой с прежним API (`CalendarPage`/`LaborCostsPage` не меняются), `QaMetricsPage` использует общий контрол со своим диапазоном (`internal/qa.RangeStart/RangeEnd`, численно совпадает с Календарём, но независимо). Контентная область ограничена `max-w-[1600px]` — ориентир на экран Full HD, а не растяжение на произвольно широкий монитор.

### Библиотека UI-компонентов (components/ui/, issue #59)

Рефакторинг от чистого utility-first (каждый компонент сам пишет строку Tailwind-классов) к переиспользуемым компонентам — начат после того, как повторы (модалка форм, попапы, кнопки, page-обёртка) накопились в 20+ местах. Правило: выносится только то, что реально дублируется ≥2 раза буквально в коде — не выдумываются переменые/варианты, которых не существует сегодня (пример осознанного НЕ-действия: `Card`/`Surface` и единый `StatusDot` не сделаны — см. ниже).

- **`Button`** (`primary`/`danger`/`secondary`/`success`/`ghost`) — первые 4 делят общую базу-масштаб (`rounded-lg px-3 py-2 text-[13px]`), `ghost` — нет (у вызывающих реально разные отступы: нав-стрелки календаря vs пункты списка).
  - **`ghost` не задаёт цвет текста сам** (только `hover:bg-...`) — цвет обязан прийти через `className` от вызывающего. Причина: Tailwind не гарантирует, что класс, который позже в JSX-строке, победит в конфликте — порядок в итоговом CSS определяется порядком генерации, не порядком в `className`. Если бы `ghost` зашивал, например, `text-secondary`, а вызывающий пытался переопределить на `text-primary` через `className`, исход конфликта был бы непредсказуем. Это реальная ловушка, найденная при миграции `PredecessorPicker` (список — `text-primary`) в один заход с `DatePickerPopover` (нав-стрелки — `text-secondary`).
  - `forwardRef` — нужен, т.к. `DependenciesField` кладёт `ref` на кнопку-триггер попапа (см. `usePopoverAnchor` ниже).
- **`Input.tsx`**: `Field`/`inputClass` перенесены из `Gantt/FormField.tsx` без изменений значения; добавлены `Input`/`Select` (тонкие обёртки над `inputClass`) и `Checkbox`. `fieldSurfaceClass` — рамка поля (border/bg/radius/padding) БЕЗ текстовых стилей, отдельно от `inputClass` — нужна элементам, которые визуально выглядят как поле, но не являются `<input>`/`<select>` (например "фейковые поля" в `GanttHeader` — диапазон дат, кнопка настроек); делать их через `Input` было бы семантически неверно.
- **`Modal`** — владеет backdrop+панелью, `<form>` остаётся у вызывающего (передаётся как `children`, оборачивается в `className="contents"`, чтобы не сломать flex-layout панели своим собственным боксом). **Закрытие по клику на фон/Escape сознательно не добавлено** — этого не было в `TaskForm`/`GroupForm` до рефакторинга, и бесшовно добавлять новое UX-поведение как побочный эффект чистого рефакторинга — не тот случай, когда молчаливое улучшение уместно.
- **`Popover`/`usePopoverAnchor`** — см. раздел «Всплывающие панели» выше.
- **`PageShell`** — один литерал (`flex h-full w-full flex-col bg-[var(--surface)]`), дублировался идентично в 5 файлах, ни одного дизайн-решения.
- **`SegmentedControl`/`SegmentedOption`** — активный токен (`bg-white ... dark:bg-[#2a2a2e]`) одинаков везде и зашит; неактивный цвет текста — нет: у `MonthPicker` он хардкод `#475569`/`dark:#666e7a`, отличающийся от `var(--text-secondary)` в тёмной теме (не совпадение, а ещё не мигрированное на CSS-переменную значение) — унификация этого хардкода не входит в скоуп issue #59, это следующий шаг после issue #48. `DensitySwitcher` не переведён на `SegmentedOption` — его активное состояние меняет только фон, без смены шрифта/цвета (третья непохожая форма), использует голую обёртку `SegmentedControl`.
- **`Badge.tsx` (`Avatar`)** — только аватар-кружки команды (`BottomStatusBar`, 2 вхождения). Легенд-пилюля там же осталась inline-классом — единственное вхождение, компонент не создавался ради одного места.
- **Осознанно НЕ сделано в этом заходе**:
  - `Card`/`Surface` — "плавающая панель" покрыта `Popover`; `EmployeeCard`'а цвета не на системе CSS-переменных (issue #48) — тянуть его в общий Card означало бы либо форсировать на переменные (отдельная задача), либо тащить одноразовые цвета в общий компонент.
  - Единый `StatusDot` — `StatusSquare` (Gantt, квадрат) и легенд-точка `LaborCostsPage` (круг) разной формы и по одному вхождению каждая; общий компонент с `shape`-пропом ради несуществующего дублирования не создан.
- **Success-кнопка экспорта в Excel** приведена к общему масштабу `Button` + получила настоящую SVG-иконку (`assets/icons/download.svg`) — на её месте была не иконка, а полупрозрачный квадрат-заглушка, и это подтвердилось даже в самом Figma-дизайне (`get_design_context` по ноде `233:7609`): реальной иконки там никогда не было, не только в коде.

### Диаграмма Ганта

- Три масштаба (Дни/Недели/Месяцы) и три плотности строк — все вычисления координат/ширин идут через единые формулы (`dateGrid.ts`: `pxPerDay`, `dateToX`, `durationToWidth`), которые ветвятся по масштабу **в одном месте**, а не по всему коду.
- В Figma есть готовый дизайн только для масштабов Дни/Недели — масштаб "Месяц" реализован с нуля (переменная ширина колонок под число дней в месяце, первая/последняя колонки — целый месяц).
- Порядок z-слоёв таймлайна (снизу вверх): подсветка выходных → заливка групповых/этапных строк → сетка дней/недель → линия "сегодня" → бары задач → sticky-хедер таблицы → замороженные левые колонки. Отход от этого порядка уже дважды приводил к багам (см. `feedback_windows_debugging_gotchas` в памяти) — при правке слоёв сверяться с комментариями `Layer N` в `GanttWorkspace.tsx`.
- **Ловушка со стеканием (stacking context):** `position: relative` без собственного `z-index` не создаёт новый stacking context — дочерний элемент с отрицательным `z-index` может "утечь" за пределы предполагаемого контейнера. Если слою нужен z-index ниже соседей, оборачивающему контейнеру нужно явно задать `z-index` (даже `z-0`), а не только `relative`.
- **Ловушка с flex-стретчем:** прямой потомок flex-контейнера без явной высоты по умолчанию растягивается (`align-items: stretch`) до высоты контейнера, а не до высоты своего контента — из-за этого `position: sticky` внутри может "заканчиваться" раньше реального конца списка строк. Лечится через `items-start` на родителе, если потомок должен расти под контент.
- Даты хранятся/сравниваются по календарному дню (см. раздел Backend выше) — `startOfDay`/`toDateInputValue` в `dateGrid.ts` переиспользуются везде, где нужно превратить `Date` в `yyyy-mm-dd` или сравнить дни без времени.

### Линии связи между задачами (Dependency Connectors, issue #39)

- Рендерится как **два независимых SVG-слоя** поверх таймлайна (`DependencyConnectors.tsx`): видимый слой под барами (`z-25`, `pointer-events: none`) и интерактивный слой НАД барами (`z-32`, пути с прозрачным `stroke` и широким `stroke-width` — хитбокс). Причина: строка бара (`GanttRowBar`) — это div на всю ширину строки, лежащий на `z-30`, и перехватывает клики по всей ширине независимо от X — единственный слой под барами клик никогда бы не получил. Баг обнаружен не по коду, а прямой проверкой пользователя ("не вижу чтобы работало выделение линии кликом мыши. ты это делал?") — более ранняя "проверка" шла через synthetic `dispatchEvent`, что маскировало реальное поведение хит-тестинга.
- Путь — ломаная "уголком" (`buildElbowPath`): вертикальный отрезок от предшественника до уровня подхода, горизонтальный подход, и (если нужно) финальный вертикальный отрезок до точки входа. `marker-end` с `orient="auto"` сам разворачивает стрелку по направлению последнего сегмента пути — направление стрелки не кодируется явно, оно следует из геометрии.
- Какой край бара использовать для выхода/входа зависит от типа связи (`edgeFor`): ОО/НО целятся в правый край преемника, ОН/НН — в левый. Точка выхода смещена внутрь бара предшественника на `edgeInset` (половина ширины дня, не меньше 5px) — иначе линия визуально сливается с границей бара.
- **Пересечение по времени → вход через верхнюю/нижнюю грань, а не левую** (правка по итогам ревью пользователем): если предшественник и преемник пересекаются по датам, вход в левую грань выглядел бы как стрелка, ныряющая в бар преемника сбоку. В этом случае вход — через верхнюю/нижнюю грань, по центру первого (пересекающегося) дня преемника. Критично: горизонтальный подход в этом случае должен идти **снаружи** бара (`TOP_ENTRY_CLEARANCE_PX` — запас сверх половины высоты бара), а не на высоте его центра — иначе горизонтальный отрезок физически проходит сквозь тело бара, и вход визуально неотличим от бокового (реальный баг первой версии фикса, найден и исправлен в одном заходе).
- Выбор линии кликом и позиция кнопки удаления — не середина пути, а реальная точка клика в локальных SVG-координатах (`getScreenCTM().inverse()` + `matrixTransform`) — иначе кнопка могла появляться далеко от места клика на длинной линии, проходящей через много строк.
- Создание связи протаскиванием мышью: маленькая ручка-хендл на правом краю бара (видна только при hover строки, `GanttRow.tsx`), `mousedown` на ней запускает отслеживание через `window`-листенеры `mousemove`/`mouseup`; целевая строка определяется хит-тестом по Y (`findRowIndexAtY` в `GanttWorkspace.tsx`). Live-превью связи во время протаскивания — отдельный пунктирный `path` (`dragPreview`), не сама будущая связь.
- Предшественник, свёрнутый в группу или отфильтрованный, — связь для него просто не рисуется (`predIndex === undefined` → `continue`); маршрутизация линии через свёрнутые группы вне скоупа PoC.

### Форма просмотра группы (GroupForm, issue #55)

- У summary-задач (групп) — отдельный компонент `GroupForm.tsx`, не `TaskForm` с условной веткой: у группы нет собственных редактируемых `start`/`finish`/`percentComplete` — это производные от подзадач, и попытка сохранить их в общей форме создавала бы иллюзию, что группу можно редактировать напрямую (бэкенд всё равно отклонит, см. Backend / `PercentComplete`).
- Отличия от `TaskForm` (решение пользователя, 3 пункта): даты — текст (`formatDayMonth`), не `<input type="date">`; чекбокс "заблокировано" убран целиком (не задизейблен) — вместо него предупреждение, если среди подзадач есть заблокированные (`hasBlockedDescendant`, обходится по дереву через `parentUid` в `GanttPage.groupInfoByTaskUid`); исполнители — не мультиселект, а список имён, собранных по вложенным задачам, а не поле самой группы.
- Общее с `TaskForm` (название, родитель, предшественники) вынесено в переиспользуемые `ui/Input.tsx` (`Field`, `inputClass`) и `DependenciesField.tsx` (список + попап `PredecessorPicker`) — чтобы логика "Предшественники" не дублировалась между двумя формами.
- `GanttPage` решает, какую форму показать (`isEditingGroup`), на основе `node.isSummary` редактируемой задачи — переключение форм происходит на уровне страницы, а не внутри одной формы через большое количество условных веток.

### Страница «Проекты» и per-project маршрутизация Ганта (issue #64)

- В Figma **нет** макета для страницы «Проекты» (проверено — `get_metadata` по странице `0:1` не находит такого фрейма среди существующих `gantt-chart-app`/`timesheet-*`/`kanban-board`/`bug-report-page`/`qa-metrics-page`) — вся страница спроектирована с нуля по существующим `ui/`-конвенциям, тот же подход, что раньше применялся к масштабу «Месяцы» без Figma-источника.
- Новая фича-папка `components/Projects/` (сиблинг `Gantt/`/`Calendar/`): `ProjectsPage` (список + модалки), `ProjectCard`, `ProjectForm` (создание/редактирование метаданных — даты/задачи не редактируются напрямую, вычисляются из задач, тот же принцип, что у `GroupForm` для summary-задач), `ImportProjectForm` (название+описание+XML-файл, `multipart/form-data`).
- Иконки индикатора отставания/редактирования — **инлайновые SVG в JSX**, не `img`-ассеты: `img` не может подхватить цвет через `currentColor`/CSS-переменную, а карточка проекта рендерится в обеих темах. Прецедент раздельных light/dark ассетов (`close-dark.svg`/`close-light.svg`) здесь не нужен — это не элемент из Figma, а собственная задумка страницы, инлайн проще и обходится без пары файлов. Цвет предупреждения (`#FF974C`) — тот же, что `overdue` в `Gantt/status.ts` (единая семантика "просрочено/отставание" по всему приложению, не совпадение).
- Каждая карточка целиком — `<Link>` на диаграмму проекта; кнопки редактирования/экспорта внутри неё — независимые `<button>` с `e.preventDefault(); e.stopPropagation()` в обработчике, иначе клик по кнопке дополнительно триггерил бы переход по карточке (тот же класс проблемы, что уже задокументирован для попапов — независимые кликабельные элементы в одной строке).
- **Вкладка «Диаграммы» стала per-project.** Раньше (issue #62) она вела на фиксированный `/gantt` без параметра; теперь маршрут — `/gantt/diagrams/:projectId` (реальная страница, `GanttPage` читает id через `useParams`), а бывший путь `/gantt/diagrams` (без id) — точка входа: `GanttDiagramsRedirect` резолвит последний просмотренный проект (`localStorage['gantt-last-project-id']`, если тот ещё существует в списке), иначе первый проект из списка, иначе `/gantt/projects` (проектов нет вообще — полезнее увидеть пустой список с кнопками создания/импорта, чем пустую диаграмму). `GanttPage` сам пишет в этот ключ `localStorage` при каждой успешной загрузке.
- Это потребовало обобщить сравнение активного пути в `Sidebar.isRouteActive` и `SectionTabs`'s `isActive` с точного `pathname === path` на точное совпадение ИЛИ вложенный путь (`pathname.startsWith(path + '/')`) — иначе группа «Гантт» в сайдбаре и вкладка «Диаграммы» не подсвечивались бы на `/gantt/diagrams/42`. Безопасное обобщение: у остальных вкладок вложенных путей никогда не было и не будет.
- `GANTT_TABS` (константа вкладок Проекты/Диаграммы/Исполнители) вынесена из `GanttPage.tsx` в отдельный `Gantt/ganttTabs.ts`; сама панель (вкладки + `ThemeToggle`) собрана в `Gantt/GanttSectionHeader.tsx` (issue #67) — общий компонент для `GanttPage` (все три его состояния: загрузка/ошибка/успех — раньше дублировался как три копии одного `div`) и `ProjectsPage`.
- **Открытие/закрытие проекта (issue #67):** кнопка-замок на `ProjectCard` — независимый `<button>` (тот же stopPropagation-паттерн, что у редактирования/экспорта), переключает `closed` через тот же `updateProject`/`PATCH`, что и правку метаданных (см. Backend). Закрытый проект — приглушён (`opacity-60`) и помечен бейджем «Закрыт». Переключатель «Открытые/Закрытые» (`ui/SegmentedControl`) фильтрует список **на клиенте** — весь список и так приходит одним `GET /api/projects`, отдельный query-параметр не нужен на текущем масштабе. Список карточек ограничен `max-w-[960px]` — по умолчанию растягивался на всю ширину страницы, не было запрошено дизайном.

### Дизайн из Figma

- Источник дизайна — фиксированный файл Figma (см. `# Дизайн` в @CLAUDE.md); для конкретных фреймов/нод — see memory (`reference_figma_gantt`).

## Git-воркфлоу для больших задач

Отдельно от базового правила "одна ветка на задачу" (@CODE.md): если пользователь просит несколько связанных изменений сделать "в одной ветке сегодня" — это временное указание на сессию, коммиты внутри всё равно разбиваются по смыслу (один коммит = одно логическое изменение), а не по времени/чату.
