# Код

## Структура папок
Код хранится в папке `src`. Она подключена к git-репозиторию.
`src\Backend` - содержит backend-файлы на Go.
`src\Frontend` - содержит веб-интерфейс на React.
`src\sql\` - хранит sql-схему для postgres и миграции. `dashbord.sql` содержит скрипт создания всей базы данных.

`samples\` - лежит в корне проекта (вне `src`, не под git). Содержит примеры данных для разработки.
`samples\project.xml` - пример XML-документа проекта (формат Microsoft Project/MSPDI) — источник данных для диаграммы Ганта на Этапе 1 роадмапа.

## Git Workflow
- Перед началом работы над таской создавать отдельную фича-ветку и привязывать её к задаче.
  - Напрямую привязать существующую ветку к issue через GitHub API нельзя (`createLinkedBranch` только создаёт новую ветку). Поэтому: создать ветку → закоммитить работу → открыть Pull Request из этой ветки в `main` с `Closes #<номер>` в описании — issue покажет связанный PR в разделе Development и закроется автоматически при мерже.
- Каждое значимое изменение оформляется отдельным коммитом с описательным сообщением о том, что изменилось и почему.
- Разные папки/модули стейджить и коммитить отдельно, с релевантными точечными сообщениями коммитов.
- Никогда не объединять несвязанные изменения в один коммит.
- Пушить в фича-ветку (origin/<название-ветки>) после каждой логической единицы работы.
- После того как фича-ветка влита в `main` (мерж PR, в том числе вручную), автоматически удалять её — локально и на origin — без отдельного запроса подтверждения.

## Комментарии в коде
Комментарии — на русском языке. Коротко, но ёмко: объяснять неочевидное (почему, а не что), не пересказывать код.

## Тестирование
- После добавления теста не удалять его в дальнейшем — тесты накапливаются как регрессионное покрытие. Удалять после использования допустимо только для одноразовых скриптов проверки/осмотра (например, раннер в `cmd/`, использованный один раз для проверки состояния БД).
